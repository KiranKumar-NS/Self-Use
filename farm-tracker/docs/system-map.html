Farm Tracker — System Map & Gap Analysis

Every rupee in this system becomes a Transaction, and everything else — dues, harvest profit, loan books, dashboards, backups — is built around that one collection. This page maps the full flow in six diagrams, then lists the missing cases found in the code and how the current architecture supports what's planned next.

1 · Big picture

System architecture

Everything runs client-side: the Angular PWA talks directly to Firestore (offline cache included), and there are no Cloud Functions. Backups run independently in Google Apps Script with a read-only service account; admin repairs run from your laptop with the admin key.

Design choice to remember: integrity lives in the client. transaction.service.ts maintains summary counters, loan.service.ts auto-creates linked transactions, and Firestore rules only validate types, roles and doc-ID shape. A buggy or old client version can drift the counters — that's why summary-reconciliation.service.ts exists.

3 · Firestore

Data model — Transaction is the hub

Nine other entities link into transactions. Summary docs are keyed {month}-{segment} / {year}-{segment} and enforced by rules, so a manager can't corrupt another segment's counters.

Two aggregation strategies, on purpose: summaries are denormalized counters (fast dashboard, needs reconciliation); dues are live queries (dues.service.ts:40,55 — always correct, no drift). Harvest profit mixes both: revenue denormalized on the harvest doc, costs queried live via linkedHarvestId. Buyer/Supplier stats are a third case — counters, now kept in step on every create/update/delete by transaction.service.ts and re-derivable by the reconciler (gap G4).
Cost entry has been pulled into the source documents. A crop activity, a harvest, an animal purchase and a vaccination each create their own expense transaction and remember its id in linkedTransactionId — edit the cost and the expense follows, clear it and the expense is reversed. Crop activities can also opt out entirely (expenseSkipped) when the material came from stock that was already paid for, which is the one case where double-counting was possible.

4 · One rupee's journey

Money flow

Six entry points create transactions — most of them are now cost fields on the record that caused the spend, not manual entries. Every write atomically increments both summary docs; pending amounts split off into Dues and rejoin the cash totals only when marked received/paid.

Custody is not investment. Loan cash sitting with a person, and undistributed income they are holding, both show as Cash in Hand. When they spend it, the dashboard marks that portion "…funded from farm cash" and keeps it out of their own net investment — so the person who handles the money is not mistaken for the person who funded the farm.

5 · Operations

Backup, deploy & update pipeline

The Apps Script backup (backup-script/Code.gs) auto-discovers all root collections, keeps soft-deleted docs, preserves Firestore types losslessly, and emails you only when something is wrong. Deploys are manual; PWA clients self-update within ~30 seconds of a deploy.

6 · What's missing

Gap analysis — 12 missing cases (7 fixed, 5 open)

Found by reading the code, not guessing. Each gap cites the file that proves it. Fixed = resolved and deployed (17–20 Jul 2026, with supplier counters wired live in the Aug 2026 QA round); G3 and G6–G9 were deliberately deferred and are still open. High = loses or hides money data today · Medium = risk grows over time · Low = quality of life.

#SeverityGapWhy it mattersEvidence
G1Fixed No partial payments on dues. Payment status is binary — received or pending. A buyer paying ₹6,000 of a ₹10,000 pending sale can't be recorded. You either mark it fully received (wrong) or leave it fully pending (wrong). transaction.model.ts — paymentStatus: 'received'|'pending'
G2Fixed No due dates or aging on dues. Notifications cover loans, tasks, budgets and schedules — never dues. A 6-month-old receivable looks identical to yesterday's. No reminder ever fires for money owed to you. notification.service.ts — no dues scan in refresh()
G3High Recurring schedules only run when the app is opened. processOverdueSchedules() fires on shell init only. Don't open the app for two weeks → no recurring transactions are created and no reminders advance. There is no server-side executor. shell.component.ts · schedule.service.ts
G4Fixed Buyer / Supplier counters can drift and have no repair tool. Summaries got a reconciliation service; counterparty stats didn't. totalPurchases, amountBySegment etc. are incremented on writes but never re-derived. Edits/deletes of old transactions slowly corrupt them. Aug 2026: supplier counters were also found to have no live callers at all — transaction.service.ts now adjusts them with signed deltas on create/update/delete. buyer.service.ts / supplier.service.ts — updateStats()
G5Fixed Consumable purchases are disconnected from expenses. Buying feed = one expense transaction and one stock movement, with no link. Double entry, and no way to verify inventory spend against the books. StockMovement has no linkedTransactionId. inventory-item.model.ts · inventory-item.service.ts
G6Medium Backup silently misses future subcollections. Root collections are auto-discovered; subcollections are a hard-coded list. Only repayments is listed. Any new subcollection (e.g. from the loan-disbursement feature) is not backed up until someone remembers to edit the script. Code.gs:34 — SUBCOLLECTION_GROUPS = ['repayments']
G7Medium Restore has never been drilled. The JSON restore path is documented but untested end-to-end. A backup you've never restored is a hope, not a backup. The _ts/_ref revival + batch-write path in SETUP.md should be proven against the emulator once. backup-script/SETUP.md · scripts/verify-backup.js
G8Medium No receipt / photo attachments on transactions. Firebase Storage is not used at all. Bills, weighment slips and mandi receipts live only on paper or in the phone gallery, unlinked to the record they prove. transaction.model.ts — no attachment field; no Storage in app.config.ts
G9Medium No server-side integrity layer. All invariants (summary math, loan balances, auto-created transactions) run in the browser. Rules validate types and roles only. An outdated cached PWA client or a bug ships wrong counters straight to Firestore. firestore.rules — no Cloud Functions in repo
G10Fixed Tag list grows forever. meta/tags is arrayUnion-only — no rename, merge or delete. Auto-generated tags (feed-jul-2026, monsoon-2026…) accumulate monthly; typo tags can never be cleaned up. tag.service.ts
G11Fixed Audit timeline capped at 50 entries. Older history is silently dropped (keeps created + last 49). Fine for most records, but a long-lived formal loan edited often will lose its early history with no export. timeline.utils.ts — appendTimelineCapped()
G12Fixed July audit leftovers. Two items from the 10 Jul 2026 audit are still open. (a) CSP headers not yet verified against the live site; (b) a summary reconciliation run hasn't been executed against production data. firebase.json · summary-reconciliation.service.ts

7 · Where this goes

Future roadmap — what the architecture already supports

The Transaction-hub design means most future features are "one more link field + one more service" rather than a rewrite. Three of the features listed here have since shipped; the remaining gaps suggest what is next.

Shipped Loan disbursement suite

Formal loans with EMI, deductions, utilization, balance transfer and personal holdings — plus cash advances that were not in the original design.

  • Built on loan-math.ts (unit-tested EMI schedules), with utilization + child-loan links in the model.
  • Advances (advances[], Jul 2026) hand unused loan cash to a person as a float: custody, settled later as spent or returned. Holder custody = utilizationRemaining − Σ open advances.
  • heldBy is mandatory; holder/source/segments stay editable, and closure zeroes unused-in-hand.
  • Embedded array, not a subcollection — so G6 (backup blind spot) does not bite here.

Shipped Animal cost tracking

Per-batch P&L, buyer management, mortality analysis — arrived alongside the Animals + Inventory merge.

  • Every stock-count change flows through one inventory-event-dialog (event / sale / death modes), so parallel entry paths can no longer double-count.
  • Purchases, vaccinations and medical records attribute their cost to the batch via costEntries → totalInvested → profit on sale.
  • New records are batches (a batch of 1 is valid); individual records remain readable and sellable as legacy.

Shipped Dues, done properly

Partial payments, expected-payment dates, aging, and dues in the notification bell — plus dashboard tiles that link straight into each tab.

  • amountReceived/amountPaid + expectedPaymentDate on Transaction; dues.service.ts stayed a live query, so no counter migration was needed.
  • Stat tiles turned cash-basis at the same time: profit counts settled money, and everything unsettled shows as Pending (To Receive) / Credit (To Pay).

From G3+G9 A small server-side layer

One scheduled executor fixes recurring transactions, dues reminders and future push notifications in a single stroke.

  • Cheapest path: extend the existing Apps Script (already authenticated, already scheduled) — or a single Cloud Function cron.

From G4+G12 Keep the counters honest

The prod reconciliation run happened (17 Jul 2026, 18 summary docs corrected) and buyer/supplier stats now update live. What is left is making it routine.

  • summary-reconciliation.service.ts is the template: re-derive from raw transactions, report drift, rewrite. Blank category keys now fall into an uncategorized bucket instead of failing the whole batch.
  • Worth scheduling rather than remembering — see the server-side layer card.

From G8 Close the paper trail

Consumable stock movements now carry their expense link (G5); receipt photos via Firebase Storage are still missing.

  • Bills and weighment slips remain on paper — Storage is not wired into app.config.ts at all.
  • The link pattern to copy is already everywhere: linkedTransactionId on the source doc + a live query.
